多人软件工厂：并发交付的新难题

一个人在笔记本上跑软件工厂是一回事，把它打开给整个组织、让许多人与许多编码 Agent 同时在同一条主干上工作，是另一回事。DevOps 运动创始人之一 Patrick Debois 在 AI DevCon 纽约站的演讲里，讲的正是这道分水岭：Tessl 内部经历六轮工厂迭代后收拢为一条全员共用的流水线，随之而来的是 PR 量暴涨、合并冲突、Agent 互相拆台，以及一个 PR 合入后其余全部重排重测、CI 开销冲上天。他沿着官方章节一路拆解当下正在成形的解法：按代码分片切分任务、把世界连同代码一起分叉、执行中重谈范围、按意图合并、推测合并，以及重建 Git 与工单系统的新一波基础设施；后半程转向人的那一面——Slack 对话如何流进工单、销售与支持如何自己把功能送进厂、提问如何变成可选项、评审如何按风险分流、失败如何被设计进去。结尾他把两条线收成一句话：Agent 共用一条主干，人共用一块看板。

Key Takeaways

  1. 单机工厂与多人共用工厂是两种问题。打开给整个组织，PR 量、合并冲突与 CI 开销同时爆炸，串行交付的老模型先在合并处断掉。
  2. 并发交付要先切分，再谈合并。按代码分片认领任务、亮明要动哪块代码，再用锁与执行中的范围重谈兜底。
  3. 合并要看意图，不只看语法。美元改分与发票合计两处改动都能干净合入，却会算出一张 129,900 美元的天价账单。
  4. 人的注意力才是稀缺资源。Agent 并行工作，人的注意力并不并行；评审要按风险分流，小改动直接放行，只把关键改动留给人。
  5. 失败要设计进去，不只想着避免。按风险路由、金丝雀与回滚之外，架构本身要能扛住出错；工厂就绪先要有测试、可观测性与上下文规则。

1. 开场：无聊的工厂，多人这个变量（约 0:00–1:28）

Debois 开场先给自己定位：他有 DevOps 与 CI/CD 的背景，看今天的软件工厂只觉得无聊——无非是虚拟机里的一段循环，吐出点东西。他认为缺了点什么，而这场演讲就是要补上缺的那一块：人们已经在 CI 交付之上叠了 AI Agent、做 AI 评审、让 Agent 写代码，可真正的变化在哪里？他的答案是把工厂从一个人手里拿出来，交给整个组织。

他把要讲的东西叫作多人工厂，也就是组织工厂：全队、整个组织共用的工厂。Tessl 内部走过这条路——起先人人自己在笔记本上跑工厂，经历了大约六轮迭代，如今收拢为一条精简的共用流水线。单人用得挺好，可一旦向组织里多人同时开放，就多了一层复杂性：跑在代码库上的 Agent 不再只属于你一个，代码库上同时有多个 Agent、受多个人指派在工作。这就是他要描述的问题，也是他选用“并发交付”这个词的原因——大家在同一时间做同一件事。

“We're all working the same thing at the same time.”我们都在同一时间做同一件事。

前提只有一个代码库，可以是多个仓库，单体仓库与否不太要紧，项目就住在代码所在的地方，大家一起在上面工作。主持人在演讲末尾的介绍里补了一句：Debois 是“DevOps 教父”，也是 DevOpsDays 的创办人——这一点与公开履历一致，他还合著了《DevOps 手册》，如今在 Tessl 负责 AI Native Dev 方向的工作。

■ 多人软件工厂（Multiplayer Software Factory）：组织内多人、多 Agent 共用同一条流水线、在同一代码库上并发交付的工厂形态。

■ 并发交付（Concurrent Delivery）：多人与多 Agent 同时在同一代码库上工作，PR 与合并彼此交错的交付状态。

2. 并发交付为什么会坏掉（约 1:28–5:17）

打开工厂的人最先听到的一句反馈是：不管以前 PR 的速率是多少，打开之后只会涨。这是自然的，但涨上去的同时张力也在涨。只给自己写代码时，所有 PR 都得自己批；开放给更多人，PR 就更多。多个合并、多个工单同时撞上同一个代码库，合并冲突不再是过去熟悉的量级，冲突本身也在变多。

更麻烦的是 Agent 之间的互相拆台：一个 Agent 在做一件事，另一个 Agent 因为另一个人提了冲突的要求，又把它 undo 掉，像一场地盘争夺战——“我要它这样”。这些在本地工厂里看不到的现象，一旦开到组织工厂就全冒出来了。最大的表现是：一个 PR 获批、一个小改动合入，其余所有 PR 都得变基、重跑测试；只因为有人合了一个 PR，大家就只能等着、等着、等着，慢得离谱。

PR 数量爆炸的同时，CI/CD 的开销也冲上了天，速度却下来了，容量不够。大家本以为打开工厂、把能力交出去是件好事，可有股力量在反向起作用。不只是功能在涨，Agent 引发的事故也变成工单，夜里跑的维护任务也叠进 PR 评审系统，压力越积越高。Debois 在这里搬出 CI/CD 时代的一句老话：如果它疼，就更频繁地做。他认为瓶颈总会断掉一处，与其等它断，不如现在就开始为它设计——因为这就是新的常态：多人、多 Agent、在代码库上并行发生。

“If it hurts, do it more often.”如果它疼，就更频繁地做。

■ 串行点（Serial Point）：流水线里一次只能过一个的环节；构建与测试可以并行，合入主干仍一次一个。

3. 切分工作，让 Agent 别互相绊倒（约 5:17–7:51）

接下来他展示了一张自称“很精致”的幻灯片，讲人们正在用什么办法拆解并发。过去领工单是在看板上认领：你做这个、我做那个；Agent 也一样，要先把工作切开。一种切法是看意图，把任务按人能理解的单位拆开；另一种切法是看代码库本身——计费那块自成一 lane，一个 Agent 做计费，另一个做别的代码，两边互不绊倒。切分的谱系很宽：从代码图谱，到文件，到函数；有的做法已经像在合编同一份 Google 文档，只合并最后一次改动。规划层面仍按功能切分，执行层面 Agent 则按逻辑块切分，图的是不踩进同一片代码。

切分之后还要认领。人在看板上说“我领这张票”，Agent 也得一样——但它不只认领工单，还要声明自己要动哪几块代码，向其他 Agent 发出信号，告诉它们哪里可能冲突。工单板上今天还看不到这层信息，但它正是在优化并发。Debois 的判断是：切分与认领这两件事，决定了 Agent 能不能在同一代码库上和平共处。

■ 代码分片（Code Splitting）：按代码库的逻辑片区切分任务，使不同 Agent 在不同片区工作、互不干扰。

■ 认领与信号（Claim and Signal）：Agent 领工单时同时声明要动哪几块代码，让其他 Agent 提前知道哪里可能冲突。

4. 分叉世界，不只是代码（约 7:51–9:11）

本地工厂里用工作树（worktree）就够了，有的用虚拟机、有的用微虚拟机，都没问题。但放到组织工厂里想一想：机器之外还有单独的数据库，还有外部世界的信息。那些不变的 API 能不能冻住？如果冻不住，Agent 一边工作，另一边有人在改它调用的 API。能冻住的东西不只是代码：上下文能冻住，Agent 跑的测试也能冻住——因为另一个 Agent 可能正在改测试。Git 只分叉代码，可 Agent 想分叉的是整个世界，哪怕只是一阵子。

隔离也有谱系。一种做法是把 Agent 放在虚拟机里起，另一种是先把虚拟机调到某个既定形态，再分叉它的内存——分叉内存比另起一整台虚拟机便宜得多，启动也容易得多。Debois 没有指定哪种做法最好，他的重点是：隔离的粒度要从“分叉一台机器”往“分叉一个世界”的方向想，API、上下文与测试都得算进去。

■ 世界分叉（Forking the World）：除代码之外，把 API、上下文与测试等外部状态一并冻结隔离，让 Agent 在稳定世界里工作。

■ 内存分叉（Memory Forking）：先把虚拟机调到既定形态再分叉其内存，比另起虚拟机更便宜、启动更快。

5. 执行中解决冲突：锁、重谈范围与合并策略（约 9:11–10:32）

Agent 干起活来还是会撞上冲突、不守规矩、互相绊倒。典型的并发手段是锁，Debois 直接把它类比成并发编程：乐观锁、悲观锁，一路走到底。但他提醒，事情不只是“我等你做完”——有的工具已经在冲突出现时让两个 Agent 执行中重谈范围：“这块我不动，你动；没事，我从你那儿拿。”这是一种执行中的同步，也是并发协作正在长出的新形态。

到了合并阶段也一样。Git 过去的规矩是：合得上就合，合不上就由用户自己去解开——“不，我不是这个意思”。现在不只在规划与执行阶段要有策略，合并阶段也要有：是把活重做一遍，还是眼看改动要来了、提前调整自己，让自己的 PR 在两者同时落地时更好合并。人们正在沿着这条谱系搭建新的策略，驱动并解决并发问题。

■ 乐观锁与悲观锁（Optimistic and Pessimistic Locking）：并发控制的两种策略，前者先做事、冲突时再处理，后者先锁定、做完再放行。

■ 范围重谈（Scope Renegotiation）：两个 Agent 在执行中发现冲突时当场重分地盘，而不是等合并时再解开。

6. 按意图合并，再到推测合并（约 10:32–12:00）

这一节是全场最具体的一幕。两个 Agent：一个说，请把总计的计算从美元改成美分；同一时间，另一份 PR 落地，给发票加了一项总计计算。两次合并在语法上都正确，都会完美合入，但合出来的不是你想要的东西。人们现在看合并，不只看代码层面合不合得上，还看意图层面合不合得上——它在我开始之后变了，就得把那部分也看进去。两个 Agent 不多时还碰不上，可跑得越多，越需要这样的策略。

幻灯片把这个例子摊开：起点都是主干上的 total()，返回 1299.00 美元；一个 Agent 把 total() 改成以美分计，129900，并修好能找到的 12 处调用、跑通测试；另一个 Agent 新加的发票页写着“$”加 total()，默认 total() 仍是美元，它的测试也全绿。两者没有冲突、全部变绿，合出来的发票却是 129,900.00 美元，而正确值应为 1,299.00 美元。工厂的抓法是：记下 B 读到了什么——它声明过“我依赖美元计价的 total()”，合并时比对 B 开始以来的变化，发现 total() 已经变了，于是判定 B 已过期，先拦住它，在新主干上重跑它的测试再放行。幻灯片脚注列出了这套思路的来源，包括 Keel、Danjou 关于为人类设计的合并队列的文章与两篇 arXiv 论文。

■ 意图合并（Intent Merge）：合并时检查改动意图是否一致，而不只看语法能否合入。

再往前一步是推测合并。假如有五个 PR 进来、十个 PR 进来，不必等它们一个个往下走：与其一个合入、其余全部变基，不如看它们的组合——这五个彼此一致，可以成组、一次执行、一次放行，再看剩下的。Agent 不只被用来写代码与做评审，也被用来更好地调度 Agent、解决冲突。串行那套“写代码、测试、提 PR、等着”的模型正在被并行化取代。

■ 推测合并（Speculative Merge）：预判一组 PR 彼此一致后成组合并、一次放行，而不是一个个串行合入。

7. 新一波基础设施：重建 Git 与工单系统（约 12:00–14:35）

Debois 把视野拉高：人们正在重建 Git、重建 Linear 这样的工单系统，都在为 Agent 的负载重做一遍新版本。有人把它叫作新的 Kubernetes——某种编排器、某种构件。过去人们为虚拟机做过同样的事，用 Kubernetes 把虚拟机调度起来；现在要为一起好好工作的代码 Agent 做同样的事。他不确定这个类比最终成不成立，但方向是清楚的：交付的基础设施正在为并发 Agent 重建。

演讲中段插进一段活动宣传：AI DevCon 将于 2027 年 6 月 7 日至 8 日回到伦敦 Moorgate 的 The Brewery，首届伦敦站 6 月售罄，11 月纽约站之后再回伦敦，早鸟票 100 英镑，现场扫二维码购买。这段约四十秒的宣传与演讲内容无关，正文不展开，细节见脚注。

8. 人的那一面：工厂开始缠着你要答案（约 14:35–19:09）

后半程转向人的并发。工厂一开，它就开始缠着人要东西：不只是等 PR 评审，还要你澄清问题、评审维护任务。Debois 说他在 Tessl 内部看到一个很有力的循环：人们很多时候从一段 Slack 对话开始——“这正常吗？我们该这么做吗？”——对话飘在 Slack 里，有时问 Agent 能不能核实一下这是否符合代码库的做法，有时到最后让讨论 Agent 把结论写成工单。Agent 还会主动 ping 不在对话里的人，因为它知道做决定需要问谁——他笑着补了一句，别来问 Patrick，请别这么做。

更有力的一幕发生在销售与支持那边。他们平常待在工程附近，客户报了问题、要了功能，就到 Slack 上喊一声；工程先用 Agent 看看能不能做出来，再问你要不要这个功能；到后来，销售与支持干脆自己问 Agent，喜欢上这个功能、直接把它送进厂。这与氛围编程（vibe coding）时代不同：那时产出的是原型，还得工程去拆解重做；现在走的是同一条流水线，带着工程的全部严谨、全部测试，用工程喜欢的方式，同时按他们想要的功能迭代。过去要等工单被分流、等工程接手、等工程评审，这条路把许多等待绕过去了。

但这里也有张力。是不是所有编码都该走工厂？Debois 说他个人觉得很烦：探索一个 spike 时还要等工单、等大家回复，他更喜欢本地 Agent，因为能更快想清楚自己要什么。反过来，Agent 卡住时怎么接手？他举了 HelixML 的例子：Agent 卡住后打开一个云端版 VS Code，全部配好，让人直接跳进去手动改一段，再关掉、继续。这个例子按他的转述处理，未独立核实。本地 IDE 与工单板之间的界线正在模糊，两边各有道理，看的是手头这块工作适合哪边。

■ 氛围编程（Vibe Coding）：凭感觉让模型快速拼出原型的做法；原型往往还得工程拆解重做。

9. 从提问到决策：决策账本该放哪（约 19:09–21:18）

工厂学会之后，提问的方式也在变。Agent 一开始问你几个问题，然后变得聪明起来：直接给你选项，因为选比想容易；也不再问“这东西在哪”，直接去找。趋势是从提问走向决策。但决策本身留下了新问题：Agent 做的决定、工单上做的决定，该存在哪？Debois 认为工单系统是错误的存放处——它需要被记在账本里、记在上下文里、记在某种别的形态里，否则下次同样的问题还会再来一遍，还得重新综合一次决定。

写技能、写上下文就是在做同一件事，工厂里也一样。存在仓库里可以，但多人同时往仓库里写，又没有一个放决策与信息上下文的好地方。眼下还没有答案，他的要求是先把它做小。这与技能的逻辑相通：给 Agent 上下文、让它把事做成，例外永远存在，平衡点就在工厂里。

■ 决策账本（Decision Ledger）：记录 Agent 与人所做决策的去处；Debois 认为工单系统不是合适的存放处。

10. 按风险评审，为失败设计（约 21:18–24:20）

评审体验与零编码冲突之间也要找平衡，两个方向可以各走极端。Debois 说他见过有人宣称“我们再也不看代码了”，他总会追问一句：你们用的什么应用？对方解释说有一套漂亮的多 Agent 对抗评审加测试。他再追问：如果生产出了故障怎么办？通常听到的回答是：没事，我们是小初创，影响不大。他的回应是：重点不是追求完美的接受率，而是评估风险。工厂里现在的做法是按风险计算来路由决策。

例子很简单：代码库里有个认证目录，动它与在网站上改一处展示，风险完全不是一个级别。验证与测试之外，现代工厂里还得有一套风险计算，决定什么可以接受。文档可以发，Agent 生成的错字不是世界末日；金丝雀测试可以先放一小部分，再看验证走多远。人们大多在优化“让失败更不可能发生”，也就是验证结果；但万一有东西漏网呢？这又回到架构：架构能不能承受失败？数据能不能回滚？版本能不能回退？它造成的副作用能不能撤销？不能只想着限制发生，还要想着发生之后怎么收拾。

幻灯片把这套做法收成四条：第一，让失败更不可能发生——测试、策略检查，且测试是 Agent 改不动的；第二，验证结果——跑起来、启动应用、证据与意图挂钩；第三，按风险路由——低风险直接发（文案与纯文档改动、只跑测试），中风险走金丝雀（BIL-142 的端点），高风险加更多验证（BIL-142 的退款行），只有关键改动（认证与支付流）才等一个人点头；第四，让犯错变便宜——功能开关、隔离单元、金丝雀、自动回滚，找到责任方、撤销改动。评审的可读性是同一条线的另一面：一份 47 个文件、增加 2,881 行的 PR，“没人会去评审它”；具名评审员 Mei 读的是五份小 PR——货币类型、端点、CSV 写入器、退款行、界面按钮——每份带测试或预览、带证据，任何一处变红先退回给 Agent，人看之前不放行。BIL-142 与评审员 Mei 均为幻灯片原貌，未独立核实。

他还回望了更早的时代：开发者曾经把 WAR 包与 JAR 包扔过墙去，不知道另一边发生了什么；当时的设计思路是，失败了能轻松回去。他希望大家也这样想：不只盯着验证与测试，也想想失败之后怎么收拾。幻灯片脚注列出了这套做法的来源，包括 Zalando 的工程文章、Debois 自己关于评审瓶颈的文章与 LaunchDarkly 的文档。

■ 按风险路由（Route by Risk）：按改动风险分级决定放行方式，低风险直接发，只有关键改动才等一个人点头。

■ 金丝雀测试（Canary Testing）：先把改动放给一小部分流量或用户，确认无事再全面铺开。

11. 收尾：工厂就绪、平台团队与下一层协作（约 24:20–27:50）

收尾处有个讽刺。Debois 说自己是公司里少数远程工作的人之一，平常听不到公司里的全部对话；工厂一开，反而是所有人都觉得跟不上节奏——新功能太多、变化太快。结果是 Slack 里的汇报变多了：“今天发生了这个，我们这么做了”，因为没有别的办法跟上。更进一步，销售与市场、支持也要跟上——更新还要按对方角色的语言裁剪。原以为不再需要沟通了，结果反而沟通得更多。

“Basically, your agent wants to fork the world for a while and not just the code.”说到底，你的 Agent 想把整个世界分叉一阵子，不只是代码。

他总结的另一条是“工厂就绪”：如果没有这些东西在位——某种测试、某种可观测性、某种上下文规则——一开工厂就会在第一阶段就手忙脚乱。Tessl 内部也已经分出一小群人专门让工厂保持运转，有点像 Kubernetes 的平台团队：你们继续做业务，他们负责让一切转下去。压力只会继续涨，代码上的并发与决策上的并发都在涨；他还看到下一层正在出现：不再是人在 Slack 上批东西，而是个人 Agent 按你的偏好、而不是按工厂的偏好去批东西——这是又一层协作。他不知道这会走向哪里，但建议是：明年再回来，做好准备；一切都会跑通，也一切都会再变。

“Come back next year. Brace yourself. It's all going to work and it's all going to change again.”明年再回来。做好准备。一切都会跑通，也一切都会再变。

结尾幻灯片把全场收成两幕：代码上的并发——一条主干给 Agent，一块看板给人；第一幕“代码上的并发”是分叉、认领、隔离、调整、重跑、检查读到什么、验证，第二幕“决策上的并发”是开始、加入、决定、评审、告知。Debois 还提到，他做的许多研究都免费放在 concurrent.cd 这个站点上，幻灯片也欢迎听众私信他索取。

“One main for the agents. One board for the people.”Agent 共用一条主干，人共用一块看板。

12. 问答：调度算法能教工厂什么（约 27:50–29:37）

问答只留了两轮。第一个问题回到开头的合并冲突：能不能从 CPU 上的调度算法里学学线程之间怎么解决冲突？Debois 的回答是：分布式系统里确实有一整套知识可以拿回来，调度也可以变成一个搜索问题、优化工作的路径——这一点肯定存在。但今天多数工厂的调度器还很简单：就是把东西跑起来。这正是他认为需要改变的一点。

第二个问题没再展开，主持人请全场再一次为 Patrick 鼓掌，演讲结束。问答之前主持人还开了一句玩笑，说 Debois 前几天告诉他、自己发明了标点符号——这是主持人的玩笑话，不是事实主张，见脚注。

讨论问题

1. 你们团队的工厂现在是单机版还是多人共用？最先被压垮的是评审、合并还是 CI 账单？

2. 按代码分片切分任务时，你们怎么划片才不让 Agent 互相绊倒——按文件、按函数，还是按业务边界？

3. 美元改分、发票合计的例子里，语法合并全绿、意图却错了——你们的合并流程今天能抓住这种错吗？

4. Agent 一边问问题一边等你回答，幻灯片说交互会话里约八成时间花在等人——你们怎么把提问改成可选项？

5. 按风险路由：哪些改动可以直接放行、哪些必须有人点头？你们的风险分级今天写在哪里？

6. Debois 说决策不该存在工单系统里——你们的 Agent 决策今天存在哪？下一个人怎么找到它？
