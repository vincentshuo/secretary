“We can build anything, but should we?”

先建作坊，再建工厂

Build the Workshop Before the Software Factory — Armin Ronacher, Earendil

Speaker: Armin Ronacher，Earendil 联合创始人兼 CTO；Flask 与 Jinja 作者

Event: AI Engineer Code Summit 演讲（Google DeepMind 赞助）

Length: 19 分 56 秒

Source: youtu.be/JNexz3Tbiu8

Technical Monograph · 精读报告 发布 2026 年 11 月 22 日 生成 2026 年 11 月 23 日

人人都在建软件工厂，Armin Ronacher 却先问了一句：我们学会在作坊里把活干好了吗？这位 Flask 与 Jinja 的作者、Earendil 联合创始人兼 CTO 带来了一整年的个人会话数据：Pi 编码 Agent 的核心支架一年没变，模型变强之后，他每百次提示要纠的手从 8.5 次降到 3.9 次，单条提示能让 Agent 跑满 14 分钟；可与此同时，他每天发的提示数纹丝不动，Agent 的工作时长却从每天 6 小时涨到 43.7 小时，一年开了 141 个项目、持续维护的只有十来个。他的判断是，瓶颈不在模型，而在人——注意力有限，维护没有变容易，外部系统也在被 Agent 的流量压垮。所以顺序应当反过来：先造一个能产出好软件的作坊，学会说"不像这样"、守住开放格式、把算力花在"好"上，再谈工厂；支架的下一步则是耐久与代码模式，让 Agent 能挂起、恢复、批量处理成千上万的请求。结尾他把整场收成一句话：我们什么都能造了，可未必什么都该造。

Key Takeaways

  1. 模型变强了，支架没变。Pi 核心工具与去年 12 月完全相同，纠错却从每百次提示 8.5 次降到 3.9 次，进步全来自模型。
  2. 注意力才是上限。每天提示数持平在 120–190 条，Agent 工作时长却从每天 6 小时涨到 43.7 小时，人跟不上机器的产出。
  3. 开得多，养得少。一年开了 141 个项目，每月持续维护的只有 6–13 个；连全自动化的项目，也会因为人不再关心而被关掉。
  4. 作坊要三样本事。敢说"不像这样"、真本事压过 Agent 本事、按自己的理解给速度限速，缺一不可。
  5. 别急着建工厂。先抵制野蛮生长、守住开放格式，再把算力花在"好"上：可验证、更快、内存安全。

1. 开场：先建作坊，再建工厂（约 0:00–1:43）

Ronacher 开场先把立场摆明：人人都在建软件工厂，他要为另一件事辩护——先建作坊（atelier / workshop），再建工厂。他拿艺术家打比方：一个出色的艺术家用上数控机床、3D 打印机与上好的电动工具，野心会随之变大，能做的东西也随之变多；软件也可以这样看。重点不是造出多得多的软件，而是造出雄心更大、质量更高的软件。他坦言自己一方也有利益在其中：Earendil 正在做 Pi 编码 Agent，所以他对支架该怎么演进有自己的立场；但他要拿出的首先是数据，是自己一整年的使用记录。

他把这场演讲的标题幻灯片收成三行：人人都在建软件工厂；我们大多数人——包括他自己——还没学会在作坊里把这些工具用好；他在乎的是志向更高的好软件，而不是批量生产的平庸之作。工厂的许诺是产量，作坊的许诺是手艺；他的整场论证，就是要把顺序颠倒过来。

■ 软件作坊（Software Atelier）：先打磨出产高质量软件的手艺、工作方式与判断力，再谈批量生产的组织形态；与"软件工厂"相对。

■ Pi 编码 Agent（Pi Coding Agent）：Earendil 旗下的极简编码 Agent，由 Mario Zechner 首创，2026 年 4 月由 Earendil 收购；核心只有读取、写入、编辑与 Bash 四类工具。

2. 支架没变，模型变了（约 1:43–3:17）

第一组数据就足够反直觉：Pi 的核心支架一年没有变过，今天的工具与去年 12 月完全相同，可它却强大得多——纯粹因为模型变好了。他说，这意味着我们所有人都在同时变强，哪怕支架上没有任何重大改动落地。过去一年半里流传的种种"更好地提示机器"的技巧与支架花招，如今大多已不再必要。他举了个自己的例子：他曾喜欢一个能让 Agent 自主朝着"提升性能"这类目标推进的插件，可用上今天最先进的模型之后，整个插件都不再需要了——能力直接长在了模型里。

他分析了自己的 Pi 会话数据：每百次提示里他需要纠正的次数，随着模型一代代变好而一路下降。幻灯片上的数字是：GPT-5.3 Codex 每百次提示纠正 8.5 次，GPT-5.5 为 7.2 次，GPT-5.6 为 5.3 次，Opus 5.5 只剩 3.9 次；按 Esc 中断计的中止次数也同步从 13.1 次降到 7.2 次。他还补了一句：GPT-6.2 的 Astra 与 Soul 在他的测试里看起来与 Opus 很接近，只是手头数据不够，没法体面地放上图。

这组数字的统计口径写在幻灯片脚注里：2026 年 3 月至 11 月他本人的 Pi 会话（临时文件夹之外），纠正按关键词启发式统计，中止以他按 Esc 计。样本是一个人、九个月，结论的适用范围也就是一个人、九个月——但方向足够清楚：进步来自模型，不来自支架。

■ 支架（Harness）：编码 Agent 外围的工具集、提示词与流程骨架；Pi 的核心支架一年未变，能力提升全来自模型换代。

3. 一条提示能走 14 分钟（约 3:17–4:47）

第二组数据讲的是单条提示能走多远。按 P90（90 分位数）计，一条提示引发的 Agent 运行时长：去年 12 月的 Opus 4.6 是 2.4 分钟，GPT-5.3 Codex 5.4 分钟，GPT-5.5 为 5.6 分钟，GPT-5.6 为 8.5 分钟，如今的 Opus 5.5 达到 14 分钟；每条提示的工具调用次数也从 19 次涨到 54 次。这改变了人与支架打交道的方式：任务跑得越久，越不能像过去那样全程盯着。

工具使用的构成也在变。幻灯片显示，在同一套支架下，模型越来越倾向于用 Bash 而不是专用工具；Opus 5.5 的工具调用里 Bash 占到 43%，读取工具只占 6%。还有一小块紫色正在悄悄变大——那是代码模式（code mode），即让 Agent 用 JavaScript 编排调用；脚注注明，在 Opus 5.5 那批会话之前，Pi 里还没有代码模式。支架的配置什么都没改，行为的变化全是模型涌现出来的。

■ P90（90th Percentile）：把数据从小到大排列后处于 90% 位置的值；此处指单条提示引发的 Agent 运行时长的 90 分位数。

■ 代码模式（Code Mode）：让 Agent 用 JavaScript 编排工具调用，而非把每一次调用都塞进上下文；调用发生在支架一侧，状态留在对话记录里。

4. 人没变：注意力才是上限（约 4:47–6:17）

模型在变，人却没变。Ronacher 说，过去一年里唯一没变的东西，至少对他自己、对很多人来说，就是我们仍然是人，仍然受限于自身最基本的能力。野心越大、机器做得越多，人就越是那个给速度定调的因素。至少对他来说，人类的注意力才是限制因素，这一点在团队里部署编码 Agent 时感受最明显：注意力就那么多，得省着用。

“We’re still limited by our fundamental capabilities.”我们仍然受限于自身最基本的能力。

不对称正在拉大：开一个新项目变得极其容易，尤其新模型一出来，人人都想试试能从 3D 游戏到自动化流程里玩出什么新花样；可维护它们并没有变容易。与此同时，我们还在给许多外部系统加压——那些系统本来就不是这场变革的一部分。GitHub 上的提交与仓库越来越多，这是看得见的；看不见的是，不少人告诉他，一些老牌网站因为 Agent 的直接访问而获得了"新生"，却完全没准备好迎接这股流量。我们一边在推东西，一边也在无意中同时推着那些还没准备好的东西。

■ 注意力上限（Attention Limit）：人的注意力不随模型能力增长；Agent 产出越多，人能消化、评审与维护的量越成为瓶颈。

5. 开了 141 个项目，养着 10 到 15 个（约 6:17–7:47）

第三组数据把这种不对称量化了。他每天主动发的提示数一年里基本持平，在 120 到 190 条之间来回波动——3 月 126 条、4 月 148 条、5 月 103 条、6 月 117 条、7 月 137 条、8 月 117 条、9 月 182 条、10 月 190 条，11 月前 9 天 120 条。可 Agent 每天为他工作的时长，却从不到一个工作日涨到了数倍于一个工作日：3 月 6 小时、4 月 6 小时、5 月 4.8 小时、6 月 5.2 小时、7 月 6.1 小时、8 月 7.9 小时、9 月 11.5 小时、10 月 14.4 小时，11 月前 9 天达到 43.7 小时——按并行会话分别累加计，11 月还没过完，曲线已经指数级上扬。

项目数也一样：一年里他新建的 Git 仓库累计 141 个（3 月 24 个、4 月 47 个、5 月 61 个、6 月 69 个、7 月 84 个、8 月 101 个、9 月 119 个、10 月 141 个），可每月持续提交 5 天以上的项目只有 6 到 13 个——3 月 6 个、4 月 13 个、5 月 9 个、6 月 7 个、7 月 9 个、8 月 11 个、9 月 10 个、10 月 11 个。他说自己在朋友里非正式地问了一圈，这是普遍趋势：定期维护一样东西很难。

他还讲了一个反例：一位朋友把一个开源项目全自动化了——工单进来，Agent 自动评审、提交、发回，看起来是把人彻底拿掉、从而扩规模的办法。可朋友最后还是把它关了：他对那个项目不再那么在乎了，想把 token 额度留给别的事。人在不在乎，决定了它的生死——哪怕一件事已经全自动，人一旦不再用它、不再照料它，它还是会死掉。

6. 作坊要什么：会说"不像这样"（约 7:47–11:32）

如果先造作坊，那作坊里最重要的是什么？Ronacher 给了三条。第一条是知道什么时候顶回去：告诉 Agent"这条路不对"。这项本事之所以关键，是因为 Agent 的奖励就是完成目标，目标达成与否一目了然——就像强化学习环境奖励模型完成训练一样；可交付出来的东西，未必是你在更长时间里真正满意的东西。提交越多、软件越大，这一点越要命：攒出一辆装满所有功能的"辛普森汽车"再容易不过，可要让内部复杂度不爆炸、让各部分真正严丝合缝，仍然得有人一边做一边盯着。

“It is very easy to basically create the Simpson car of all the features in a software.”攒出一辆装满所有功能的"辛普森汽车"，再容易不过了。

第二条是"真本事"与"Agent 本事"的区别。有经验的软件工程师与没有经验的人用同一套系统、提同样的提示，产出质量截然不同。他举的例子很私人：儿子现在会给他正在一起做的项目提 PR，质量上的差别一目了然——孩子不是软件工程师。他也从很多人那里听到同样的抱怨：在真正要紧的场合，屋里其他人直接问 Agent 要答案，对系统在干什么、对自己正在解决的根本问题都不再有真正的理解。这很让人沮丧。所以速度也得按自己的理解来限速：他开始在会话轨迹里找一个固定的钩子点，在收尾之前介入——具体做法是，让 Agent 在进入验证之前（大约 70% 的进度处）先给他一份简短的执行摘要，外加一份排版整齐的 HTML 页面，讲清楚它正在做什么。尤其新模型写出的文字不再那么难读之后，这个办法让他即便不再逐行读代码，也能跟上进度。

第三条是别把软件一遍遍重写：他坚信少用依赖、多自己写代码，而 Agent 革命恰恰成全了这一点——自己写的那部分，如今可以由 Agent 代劳而不必引入一堆外部依赖。少依赖、自己写，是作坊手艺的一部分。

■ 真本事与 Agent 本事（True Skill vs. Agent Skill）：人对系统真正的理解，与只会驱使 Agent 出活之间的差别；同一套系统在两种人手里产出质量截然不同。

■ 辛普森汽车（Simpson Car）：《辛普森一家》中荷马设计的什么都想要的汽车：功能堆砌、彼此打架；此处指只求目标达成、不顾内在一致的软件。

7. 别让野蛮生长毁了互操作（约 11:32–15:17）

作坊之外的另一面，是克制。他用了一个德语词：Wildwuchs，野蛮生长——不受控的蔓生。Agent 让每个人都能实现任何想要的格式，可格式一多，解读就分叉：最近流传的一篇博客讲的就是一个被精心构造的 tar 归档，不同的 tar 实现读出不同的内容。我们真正想要的是标准、共同规范、共同文件格式；可让 Agent 实现任何格式太容易了，分歧也就随之而来。难处往往不在技术，而在人怎么就"文件里该有什么、该怎么实现、该怎么解读"达成一致——可以有多种解读，而达成一致本身就是难题。

他设想了一个未来：人人都有自己的 Photoshop 克隆版，却再也没法互相发文件，因为大家分叉得太远了。协作的难度一点没变，只是换了个样子：开源项目里人与人之间的协作越来越少，分叉却越来越多——因为开个分叉比把改动推回上游容易得多。幻灯片把这页收成四行：有时自己造轮子对生态有害；"Wildwuchs"损害互操作；开放协议、规范与文件格式有用；但协作仍然慢得要命，因为它是人的事。

“Collaboration between humans is as hard as it has ever been.”人与人之间的协作，和从前一样难。

所以他主张把新得的力量花在"好"上，而不是花在"多"上。幻灯片列了三条：更多经过验证的软件——最近可验证软件确实爆发式增长，虽然技术栈还没完全到位，但值得往这个方向推；更多更快的软件——他很高兴看到那么多人想造从根本上更快、内存效率更高的软件，多年来看着内存被浪费的沮丧终于有了出口，越来越多的人开始用原生语言重写东西，而不是再套一个 Electron 壳；更多内存安全的软件——他喜欢 Rust，也喜欢内存安全正在成为趋势，好的模型能找出安全问题，这本身就是有力的论据。

■ Wildwuchs（野蛮生长）：德语词，指不受控的蔓生；此处指各家自造格式、互不兼容的失控扩张，损害互操作。

■ 可验证软件（Verified Software）：带形式化证明或强验证的软件；Ronacher 认为值得投入，但技术栈尚未完全到位。

8. 支架还能往哪走：耐久与代码模式（约 15:17–19:06）

最后一大段回到支架本身：模型已经这么好，支架的下一步该往哪走？第一件事是耐久（durability）。两分钟的任务，你愿意守着它，坏了就手动重启；可如果 Agent 要在一夜之间处理成千上万个工单，你就得让它能自己重启。Earendil 相信"耐久 Agent"：能启动、能停止、能挂起、能回来。动机不只是任务变长，还有算力与成本：大家都受推理成本约束；按原始 token 价格走弹性排期能拿到相当大的折扣，代价是有时几分钟没有 token 进来——那就该把 Agent 与沙箱一起挂起，别让其他昂贵的资源空转。模型越好，越值得重新想想怎么聪明地用资源。

■ 耐久 Agent（Durable Agent）：可暂停、恢复、挂起的工作流式 Agent；任务不必一次跑完，人几小时后再回复也不必干等。

■ 弹性排期（Flex Scheduling）：以等待换取推理折扣的计价方式；token 有时几分钟不来，Agent 与沙箱应当随之挂起以省资源。

第二件事是代码模式与分类模型。Pi 出来时有个很强的信念：Bash 就是你需要的一切，这一点他至今基本认同；但现在出现了编排子 Agent 的需求，也出现了非语言模型的需求——决策模型、分类模型，比如 Jev 与 Clef。这时就得开始组合工作流。这个想法最初来自 Cloudflare 的人：与其把成千上万个工具塞进上下文，不如除了 Bash 之外再给 Agent 一段 JavaScript，让 Agent 本来要做的工具调用都经由 JavaScript 发生，从而更好地编排它们。这起初像个好奇的点子，如今已变得出奇地有用：Codex 与 Pi 等支架已经支持，支架可以在不经过低效上下文的情况下，编排大规模的工具调用。

分类模型是另一块拼图：它们不占活跃的 KV 缓存，又便宜又快，能接手那些过去太贵或太慢的问题。Ronacher 的用法是：有了代码模式，支架可以造出带决策点的小工作流——比如要处理 3,000 封进来的客服请求，每个 if 条件都走一遍 Jev，判断是派给 Agent 干活、还是要客户再补充反馈；几千个问题，几分钟内跑完，放在编码 Agent 里做要花几小时。他提醒，这里的关键不是模型本身，而是编排方式变了：判断不再经过上下文，而是由专门的小模型在循环里完成。

■ 分类模型（Classifier Model）：只做判断、返回选项与分数而不写散文的小模型，如 Jev 与 Clef；便宜、快速，宜从代码模式与循环里调用。

9. 收尾：能造一切，未必该造（约 19:06–19:56）

结尾幻灯片只有一句话："We can build anything, but should we?" Ronacher 留下的想法是：既然我们现在什么都能造了，也许恰恰不该什么都造——而应当朝着更让人享受的、在许多方面也更雄心勃勃的软件去努力。作坊先行，工厂随后；手艺先行，产量随后。

“Now that we can build everything, maybe we should not.”既然我们现在什么都能造了，也许恰恰不该什么都造。

全场 16 张幻灯片，分属四个部分：支架稳定、工厂的规模、作坊、支架还能往哪走。数据都来自他一个人、2026 年 3 月至 11 月的 Pi 会话；结论也首先是他一个人的结论。但正因为样本就是他自己，数字才显得诚实：模型在指数级变强，人却还是原来的人——而这，恰恰是作坊应当先行的理由。

讨论问题

1. 你的支架多久没变了？如果模型进步本身就能带来能力提升，你的团队还在为什么而改支架？

2. 每百次提示的纠错次数、单条提示的 P90 运行时长——你会用什么数字来衡量自己与 Agent 的配合？

3. 过去一年你开了多少个项目、养着几个？注意力花在哪里，决定了什么能活下来？

4. "真本事"与"Agent 本事"：你最近一次对 Agent 说"不像这样"是什么时候？当时凭什么判断？
