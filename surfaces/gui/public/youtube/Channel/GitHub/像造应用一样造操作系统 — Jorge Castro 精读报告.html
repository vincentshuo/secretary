像造应用一样造操作系统

What open source can teach us about agents in CI/CD — Jorge Castro, GitHub Universe 2026

Speaker: Jorge Castro，CNCF 开源社区工程师与开发者关系（Cloud Native Computing Foundation）

Event: GitHub Universe 2026 演讲

Length: 15 分 13 秒

Source: youtu.be/bUhCBYi4dys

Technical Monograph · 精读报告 发布 2026 年 11 月 21 日 生成 2026 年 11 月 22 日

如果把操作系统当作应用来造，会发生什么？CNCF 的 Jorge Castro 在 GitHub Universe 2026 的舞台上，用他自己的项目 Bluefin 给出了答案：一个 Linux 操作系统可以像 Docker 镜像一样构建、推送、拉取与启动，更新来自镜像仓库，而不是包管理器。Bluefin 走到第五年，撞上的却是另一件事：智能体来了。Copilot 的修错按钮一次点下去居然管用，贡献者随之涌入，维护者反而被淹没——有人愤而退出，有人在印度与他在同一时间各自动用智能体改同一份代码，六小时的高速推进换来两天的合并冲突。Castro 的回答不是封禁智能体，而是给智能体立规矩：用 Hive 把一群智能体编成开发团队，用两份贡献者指南分别管人与机器，让五位智能体评审员加两位人类先看过每一份拉取请求，最后仍由人按下合并的按钮。他的收束只有一句反常识的判断：这对开源是好事还是坏事？答案是肯定的。

Key Takeaways

  1. 操作系统可以像应用一样造。Bluefin 把 Fedora 装进容器镜像，用 bootc 启动，更新从 ghcr.io 拉取，构建一次操作系统镜像约 45 分钟。
  2. 智能体需要指引，而不是放任。没有规则的智能体只会制造混乱；维护者先被 500 份陌生人的拉取请求淹没，再被互相冲突的改动拖垮。
  3. 个人用智能体走不远，规模化要靠编排。Hive 把监督者、CI 智能体与评审智能体编成一支开发团队，约每十分钟巡查一次仓库。
  4. 文档要写两份：一份给人，一份给智能体。有推理算力的贡献者按智能体贡献者指南行事，工作由 Hive 分派，而不是各人随意找活。
  5. 人永远按按钮。分流、设计与最终批准留在人手里；拉取请求的数量不再是衡量贡献的尺度，专业判断才是。

1. 开场：智能体星球，与一个操作系统项目（约 0:00–0:57）

Jorge Castro 走上 GitHub Universe 2026 的舞台，先报了自己的身份：他在云原生计算基金会（CNCF）工作，隶属 Linux 基金会，所在的团队负责托管与指导 250 多个开源项目。今天他代表的是自己的业余项目 Bluefin，一个他亲手推进了智能体化改造的 Linux 操作系统。演讲的标题是“智能体星球”，副题是开源能教会我们关于 CI/CD 智能体的事——他开场先给台下指了一条别的路：英伟达捐赠的 Open Shell 可以把智能体放进沙箱里运行，他建议在场的人都用上沙箱，而不是像他那样裸奔。

他顺带提了一句日程：两周后就是 KubeCon，欢迎大家去项目展馆找他。时间点对得上：GitHub Universe 2026 在十月底举行，KubeCon 北美站随后在十一月中旬开幕。Castro 的履历也与他自述的身份一致：他在 Canonical 工作了约十年，参与建设 Ubuntu 与 Ubuntu Server，自 2004 年起就在 Ubuntu 社区工作，后来经 VMware 转入 CNCF；Ask Ubuntu 问答站就是他参与创办的。

需要先说明本片的画面形式：整场演讲只有一个固定机位对着讲台，幻灯片并不出现在画面里——演讲者口头提到的幻灯片、二维码与拉取请求列表，观众只能听他描述，看不到画面。因此本报告的四张关键帧取自同一固定镜头的开场、中段与收束四个姿态，内容以转录稿为准，幻灯片上的数字无法像往常一样逐图核对。

2. Bluefin：把操作系统装进容器镜像（约 0:57–2:42）

Bluefin 是一个装在你电脑上的 Linux 操作系统，约有五年历史，是 Castro 心目中 Linux 该有的样子。它基于 Fedora，构建方式借用了容器那一套：先从 Fedora 基础镜像出发，加一句安装命令装上喜欢的软件包，再把文件复制进去，久而久之就成了一个操作系统。负责把容器镜像变成可启动系统的工具叫 bootc，由红帽捐赠，现为 CNCF 沙箱项目，CNCF 页面记载其于 2025 年 1 月 21 日被接纳。

■ bootc（Bootable Containers）：把 OCI 容器镜像变成可启动操作系统镜像的工具，系统更新随镜像一起从仓库拉取，而不是逐个安装软件包。

关键在于，操作系统装在裸机上、真实运行，唯一的区别是更新的来源：系统更新来自镜像仓库，地址是 ghcr.io/bluefin:stable。Castro 的比喻是，假如你会构建 Docker 容器，那你就会构建 Bluefin——只不过镜像里多了一个内核，电脑可以直接从它启动。bootc 生态里最出名的是游戏向的 Bazzite，据 Castro 说，目前野外已有超过十万台正在运行的 bootc 设备，真实用户与游戏主播都在用。他还开了那句每年必有的玩笑：这就是你们的“Linux 桌面之年”。

■ Project Bluefin：基于 Fedora 的桌面 Linux 操作系统，以容器镜像分发与更新，隶属 Universal Blue 伞形项目；同门还有游戏向的 Bazzite。

在智能体到来之前，Bluefin 的构建方式已经把 GitHub Actions 用到了头：矩阵构建、懒加载、缓存加速，一次操作系统镜像构建仍要大约 45 分钟。Castro 的说法是，他们已经把“前 AI 时代的 GitHub”用到了极限——然后 AI 就来了。

“We had maxed out pre-AI GitHub.”

我们已经把前 AI 时代的 GitHub 用到了头。

这句话值得停一下：Bluefin 的特殊之处在于，它从一开始就是按云原生方式造的操作系统——镜像、仓库、CI 流水线全是现成的。所以当智能体进入 CI/CD，Bluefin 不是从零学起，而是直接撞上了下一个问题：流水线本身还能不能装下智能体。

3. AI 来了：红色流水线上的“帮我修一下”按钮（约 2:42–4:45）

转折来得悄无声息。先是 Copilot 的按钮出现在各处，然后有一天，一条变红的 GitHub Actions 流水线旁边多了一个按钮：“帮我修一下”。Castro 的第一反应是不信，点下去之后发现它居然管用。从那以后，团队开始用 Copilot 的聊天模式，给它指派议题、让它修东西，但始终没有形成什么章法。

“There's no way this works.”

这不可能管用。

真正的冲击发生在社区层面。有人因为这件事退出项目，留下的话大意是“你们怎么能把我们卖了”；与此同时，另一些贡献者跑来说自己手里有推理算力，很想用上这些工具，却不知道该怎么做。Castro 承认，当时整个项目确实不知道该怎么办。Bluefin 里还专门放了一幅真人艺术家的画，用来呈现这种撕裂与两面性——拥抱 AI 的人走了，反对 AI 的人也走了，中间的人站在原地。

他的处境还有一层现实考量：作为开源维护者，他没法简单地禁止这件事。安全角度上，坏人反正已经在用智能体，他没有选择，只能学会它；而作为一个还没成为专家的维护者，他也不愿在自己还没搞懂之前就告诉别人不许用这个工具。于是 Bluefin 采取了观望策略：不禁，也不乱用，先学会。

4. 第一条教训：智能体需要指引（约 4:45–7:43）

这场演讲的第一条教训只有一句话：智能体需要指引。开源维护者负担过重的故事人人都听过，标准版本是这样的：你运营一个开源项目，然后收到 500 份来自陌生人的拉取请求，全是想把你的项目用 Rust 重写一遍。Castro 说这句每次都引得满场大笑——但笑完之后是混乱。有些项目膝跳反射式地全面禁止 AI，Bluefin 没有，因为他们自己也不会用。

“Agents need guidance.”

智能体需要指引。

更麻烦的是，智能体在个人手里好用，两个人同时用就失控。Castro 讲了一个实例：一位在印度的贡献者也在用智能体，而他自己也在用。六小时里他推进得飞快，等对方醒来准备进入评审周期时，一切都太晚了；他要是有一天没看对方两天前提交的东西，接下来还要再花两天去撤销合并、解决冲突。速度本身成了问题：智能体让一个人快到队友跟不上的程度。

这个例子点出了全场真正的论点。智能体不是把个人生产力乘以几倍就完事了，它改变的是协作的节奏：写代码变快了，评审、同步与合并跟不上，快的那个人反而把慢的那个人甩出了协作圈。没有编排的智能体，等于给每个贡献者发了一台没有红绿灯的跑车。

于是 Bluefin 做了 GitHub Universe 上很多人都在做的事：引入一类叫作“智能体开发生命周期”（ADLC）工具的东西。他们选的是 Hive。Castro 强调，他不会指定你用哪一个——市面上有太多，仍处于西部拓荒期。但他看重一点：Hive 正在成为 CNCF 沙箱项目，也就是说它最终会落在一个厂商中立的基金会里，所有人都能参与。CNCF 的项目页记载，Hive Commons 于 2026 年 9 月 29 日以沙箱级别被接纳——演讲者说的是“正在成为”，实际接纳日期比演讲还要早几天。

■ 智能体开发生命周期工具（ADLC, Agentic Development Life Cycle）：编排一群编码智能体的工具，负责分派任务、驱动循环、评审与合并，Hive 是其中之一。

■ Hive：CNCF 沙箱项目，把多个编码智能体编成一支开发团队的操作面；演讲时正在成为 CNCF 沙箱项目，CNCF 页面记载的接纳日期为 2026 年 9 月 29 日。

5. Hive：把一群智能体编成开发团队（约 7:43–10:45）

Hive 的界面初看吓人：全是循环与看板。但原理并不复杂。你把推理接口与 GitHub Copilot 账号接进去，它就像一支软件开发团队那样运转。团队里有一位“监督者”，约每十分钟启动一次，巡查全部仓库，发现某个仓库的 CI 变红了，就派一位 CI 智能体去处理，处理完给你发一份拉取请求。起步可以用手动模式，只给建议；也可以走到完全自主：评审、落地、合并、测试、发布到生产，全由智能体来。

■ 监督者智能体（Supervisor）：Hive 中约每十分钟巡查一次各仓库的智能体，发现 CI 变红即分派 CI 智能体去修复并提交拉取请求。

Castro 问了台下一个问题：有多少人觉得，把完全自主的智能体方案直接发到真实用户设备上是个好主意？然后他自答：现在你们明白我有多害怕了。Bluefin 的镜像跑在十万台真实设备上，一次错误的自动发布不是测试环境的红灯，而是别人电脑上的故障。这是整场演讲里最诚实的一刻：编排工具的能力边界，恰恰就是维护者敢不敢放手的问题。

与此同时，Hive 也在解决另一个问题：把闲置的推理算力分给有活干的人。贡献者 Kyle Rankin 用本地模型为项目本身提了数页拉取请求；Hive 则把任务分派给手头有多余推理算力的贡献者。GitHub 向 CNCF 的维护者捐赠 Copilot——Kubernetes 等项目都能用上不限量的 Copilot——Bluefin 便拿这个机会做实验：用前沿模型设计流程、把流程写成文档、反哺 Hive 本身，并向 Copilot 团队反馈以压低成本。Hive 内置的“洞穴人模式”也是成本工作的一部分，面向开源维护者，但演讲没有展开它的具体做法。

他还放了一段二维码，链接到一段六分钟的视频：Bluefin 的仓库从手动模式走向自动模式的可视化，配的是重金属配乐，纯属图个乐。但这段视频的意义不在音乐，而在它记录的东西：一个真实项目，是怎样一步步把控制权交出去的。

6. 好还是坏：答案是肯定的（约 10:45–12:47）

九月份的数据先摆出来：112 位贡献者，12,000 份拉取请求，其中 1,400 份发生在九月。Castro 拿 Home Assistant 作对照：对方告诉他，他们一个月大约 2,000 份拉取请求。这些数字在他嘴里不是成绩单，而是问题本身——当拉取请求以这个速度涌入，维护者该怎么活？

Bluefin 的办法是反过来利用这股洪水：不再等陌生人随机出现、自己找个“很酷的东西”来改，而是给智能体写一份专门的贡献者指南，与给人类的那份并列。手里有推理算力的贡献者按指南行事：智能体会收到指令，然后自动去做被指派的事。与其强迫人们改变行为——Castro 的比喻是，他父亲至今也不明白电子邮件到底是怎么回事——不如直接拥抱这个新世界，迎头带路。

人们总问他：这对开源是好事还是坏事？他的答案是：是的。文档是最重要的东西。早在 AI 之前，他们给 GitHub 团队的反馈就一直是通知太多——现在更糟，他的做法是“通知破产”加上标签筛选，切出自己需要的东西。他还抛出了一个更大的设想：为智能体造一个 SETI@home。许多公司想回馈开源却不知道怎么做；老板说月底可以捐出推理算力，可推理算力闲在那里没人用。能不能把这些分散的算力聚起来，像 SETI@home 聚合闲置算力那样，为公共项目工作？Kubernetes 做不了这个实验，因为它必须受到保护；Bluefin 这样的小项目，正好拿来当试验场。

■ SETI@home 式众包：演讲者的设想，把各家公司闲置的推理算力像 SETI@home 聚合闲置 CPU 那样聚起来，为开源项目工作，而不给维护者添乱。

“Is this good or bad for open source? The answer is yes.”

这对开源是好事还是坏事？答案是：是的。

这个回答不是抖机灵。它点出了整场演讲的立场：智能体对开源既是洪水也是水源，问题从来不是要不要它，而是由谁、在什么规则下用水。禁令挡不住洪水，指南与编排才能把水引到田里。

7. 人在环内：分流、评审与按按钮的手（约 12:47–14:15）

Hive 协调各智能体之间的工作，各个智能体自己干活，评审智能体审阅所有进来的拉取请求并留言。等 Castro 自己看的时候，一份拉取请求已经被五位智能体与两位人类评审过。工作方式随之变了：他发现自己淹没在评审工作量里，重点不再是实现，而是评审。

但有三件事他坚持留在人手里。第一是分流：由人来决定哪些事值得做，自动化分流试过，效果不好。第二是设计：人仍然要设计软件，一位资深成员先把关；他们正在回到“先写规格”的做法，因为规格能让智能体产出更好的结果——他自嘲说，大学时的计算机教授也会提醒他，本来就该这么做。第三是批准：永远由人批准。用他的话说，担责任的是他的脖子，按按钮的人是他。

“It's my neck on the line and I'm the one that pushes the button.”

担责任的是我的脖子，按按钮的人是我。

管理对象也变了：他现在管理的不是议题与拉取请求，而是队列。每天的问题不再是“今天有哪些拉取请求”，而是“我们在看代码的哪个区域”——把那个区域的所有议题与拉取请求放在一起批量处理，量大到要用智能体先汇总一遍。专业判断仍然是门槛：哪怕你捐出推理算力，也得懂自己在说什么；如果你回来评审时根本不知道自己发了什么，他不会合并。不是所有拉取请求都会被接受。

■ GitHub Actions：GitHub 内置的持续集成与持续交付服务；Bluefin 用它构建操作系统镜像，一次构建约 45 分钟。

8. 收束：贡献度的新刻度（约 14:15–15:13）

最后是衡量标准的问题。他们不得不发明新的方式来展示图表、激励贡献者。他很自豪地宣布：1,200 份拉取请求，干得漂亮——然后立刻提醒大家，拉取请求已经不重要了。团队正在尝试新的贡献者排行榜，奖励的是人在关键时刻介入、推翻智能体决定的行为；他甚至从电子游戏里找灵感，研究 Fortnite 是怎么让玩家保持参与感的——提交不再重要，拉取请求不再重要，议题也不再重要，那么到底什么才重要？他坦言自己也不知道，还在摸索。

演讲的收束回到文档：给人的文档与给智能体的文档，两者都需要上下文，不管使用者自己知不知道。最后他列出自己在用的工具：BuildStream——一个与 bootc 很合拍的 Apache 项目——以及 freedesktop SDK 的库；如果你想造自己的操作系统，这些全都现成可用，而且全部厂商中立。BuildStream 是 Apache 软件基金会的软件集成工具，freedesktop SDK 自 18.08 版起就用它构建，这两点已经核实。

■ BuildStream：Apache 软件基金会的软件集成工具，与 bootc 搭配构建操作系统；freedesktop SDK 自 18.08 版起用它构建。

整场演讲没有给出一行代码，也没有演示任何产品功能。它讲的是一次真实的组织变革：一个把操作系统当作应用来造的项目，如何在智能体涌入之后，重新学会管理速度、评审与信任。Castro 的答案可以收成三句：给智能体立规矩，而不是禁令；把编排、文档与评审做成基础设施；最后按按钮的手，永远是人的。

讨论问题

1. Bluefin 把操作系统做成容器镜像：如果操作系统更新像应用更新一样来自仓库，出了问题该回滚镜像，还是修单个软件包？哪种更适合桌面用户？

2. 智能体让一个人六小时推进到队友跟不上的程度：协作工具应该给速度设上限，还是给慢的人配加速器？上限设在哪里才合理？

3. Hive 的完全自主模式能评审、合并、测试并发布到生产：对跑在十万台真实设备上的系统，哪些环节永远不该交给完全自主？

4. 两份贡献者指南——一份给人，一份给智能体——如果两份指南对同一件事说法不同，以哪份为准？谁来裁决？

5. 拉取请求的数量不再衡量贡献：如果提交、拉取请求与议题都不再重要，什么样的新刻度既能激励人，又不会被智能体刷量？

6. 公司想捐推理算力回馈开源，却不知道怎么做：SETI@home 式的众包需要什么样的治理，才能不把维护者淹没在更多的拉取请求里？
